# YORU 4.17.2 — технический аудит и план улучшений

Дата: 2026-09-08. Основа: **только `handoff/YORU-4.17.2-stable-source.zip`**.
Ветка работы: `arena/01a0828d-animmmemmemwm`.

## 1. Вывод

У приложения уже есть полезная основа: native Media3, офлайн HLS/DASH, ограниченные кэши, быстрый агрегатор источников, lazy-хранилище, SQLite WAL, отмена части экранных задач и кэширование вкладок. Переписывать всё на другой стек не нужно.

Но «stable» — имя архива, а не доказательство отсутствия ошибок. Основные препятствия скорости находятся **не в недостатке потоков**, а в синхронных операциях на UI, повторном построении интерфейса, блокировках, повторном discovery и нестрогой отмене запросов. Отдельно требуется привести в порядок воспроизводимость сборки и хранение подписи.

Рекомендованный порядок: безопасность поставки → воспроизводимая база → изображения/очереди/прогресс → запуск видео → карточки/календарь → постепенное разделение архитектуры. Не менять одновременно дизайн, источники, алгоритм озвучек и плеер.

## 3. Критичные вопросы поставки

### A01 — подпись приложения хранится в старом исходном архиве — P0

**Факт:** `.github/workflows/build-apk.yml`, шаг `Restore release signing files`, извлекает `owner-signing/*` из `YORU-android-2.0.1-source.zip`. В списке файлов этого старого ZIP присутствуют `signing.properties` и `yoru-release.jks`. Значения секретов в ходе аудита не читались и не копировались.

**Риск:** если этот архив доступен посторонним, ключ подписи следует считать потенциально раскрытым. `.gitignore` не защищает секреты, уже помещённые внутрь отслеживаемого ZIP. Простое удаление ZIP из текущей версии не удалит его из истории и чужих копий.

**План:** закрыто проверить доступность и происхождение ключа; переносить signing в защищённые GitHub Actions secrets/окружение; запретить приватные signing-файлы в source ZIP. Если доступ подтверждён — согласовать план ротации с учётом способа распространения и совместимости обновлений Android. Не менять ключ автоматически: это может сломать обновление установленного приложения. Очистка истории — отдельная согласованная операция, не выполнена этим аудитом.

### A02 — ZIP не самодостаточен для заявленного workflow — P1

`settings.gradle` включает `:yuroguard`, но каталога этого модуля нет в ZIP. Workflow требует старый ZIP с подписью, которого в передаче 4.17.2 также нет. В зависимости от Gradle отсутствующий модуль может дать ошибку конфигурации либо пустой проект; это не проверено сборкой. В любом случае конфигурация не соответствует содержимому.

Workflow и старый AGENTS указывают чужую для этой сессии ветку `arena/01a07147-animmmemmemwm`. Запускать такой workflow без исправления опасно: он может записывать APK не в текущую ветку.

**План:** отдельный YORU-only комплект, Gradle-конфигурация только его модулей; независимая debug-сборка без приватных файлов; release signing из CI; публикация только в текущую ветку. Проверять сборку именно из чистой распаковки source ZIP. Оригинальный стабильный ZIP оставить неизменным.

### A03 — документация расходится с кодом — P1

Root README описывает 4.15.0, SESSION_STATE — 4.12.7, выбранная база — 4.17.2. AGENTS требует неблокирующий iframe, но текущий player фактически ориентирован на resolver/native. Нельзя слепо считать исторические инструкции описанием реализованного поведения. Нужны manifest релиза, SHA-256, source commit, versionCode, CI run и список известных ограничений для каждой выдачи.

## 4. Производительность и стабильность

### A04 — постеры читаются и декодируются синхронно — P1, максимальная отдача

`ImageLoader.java:21,26–29`:

- Конструктор удаляет старые папки и создаёт cache directory; вызывается из `Application.onCreate`.
- `loadInternal()` при disk hit сразу вызывает `decodeFile()`. Этот метод вызывается при построении UI/биндинге карточек.
- Нет RAM LRU декодированных bitmap. Повторный показ того же постера снова читает файл и декодирует картинку.
- `BitmapFactory` декодирует полное изображение в ARGB_8888, без `inJustDecodeBounds`/`inSampleSize` под размеры карточки.
- Ограничение входа 12 MiB не ограничивает размеры декодированного bitmap. Например, 4000×6000×4 ≈ 91,6 MiB только на пиксели, без временных копий.
- Waiters держат сильные ссылки на ImageView до окончания задачи; tag-check спасает от неверного изображения, но не от лишней работы/удержания закрытого экрана.

**Изменить:** bounded RAM LRU по байтам; decode/disk/network только на image executor; декодирование под целевые размеры; ключ `(URL, size, transform)`; отмена подписки при recycle; удаление пустых подписок, проверка generation перед записью на диск. Не снижать качество полноэкранной картинки ради сетки.

**Проверка:** 10 проходов длинного каталога, тёплый/холодный кэш, быстрый уход с экрана, большие картинки, low-memory устройство. В StrictMode не должно быть disk read на UI в image bind.

### A05 — CallerRunsPolicy может перенести сеть на UI — P1

`YoruApp.java:23–26`, `ImageLoader.java:17`: очереди ограничены 256/260, но политика переполнения — `CallerRunsPolicy`. Когда очередь и max-потоки заняты, задача выполняется в вызывающем потоке, в том числе UI.

Важно: `ThreadPoolExecutor` сначала заполняет очередь после core threads и лишь затем растёт к max. Поэтому увеличение max с большой очередью не ускоряет обычную очередь запросов.

**Изменить:** отдельная политика backpressure: отменять устаревшие image/search jobs, дедуплицировать одинаковые задачи, отклонение обрабатывать явно. Критичные сохранения не отбрасывать: отдельная последовательная очередь. Не заменять всё одной `DiscardPolicy` и не блокировать producer/UI.

### A06 — прогресс сериализуется и шифруется на UI — P1

`PlayerActivity.java:113,124,127`: `save()` выполняется в lifecycle/timer-пути, ограничение 3500 ms. `SecureStore.progress()` синхронно обновляет JSON, пишет favorites/history/settings, перестраивает индексы и вызывает SQLite `progressMirror()`.

`SharedPreferences.apply()` асинхронен только в части записи preferences на диск: JSON-сериализация, AES/GCM и SQLite остаются в вызывающем потоке. Обновление widget после каждого сохранения добавляет работу.

**Изменить:** UI фиксирует небольшой snapshot; последовательный writer сохраняет только изменённые поля, объединяет промежуточные события. Отдельно гарантировать порядок и финальный checkpoint на смене эпизода/паузе; не полагаться только на onDestroy. Widget обновлять при значимом изменении, а не каждые несколько секунд. Перед миграцией проверить сохранность старой коллекции/истории.

### A07 — глобальная блокировка загрузки эпизодов — P1

`ApiRepository.java:187`: весь `loadEpisode()` — `synchronized`, внутри возможна сеть. Prewarm следующей серии, скачивание и текущий playback одного repository могут ждать друг друга.

**Изменить:** single-flight на ключ эпизода, короткие блокировки только для публикации результата, network вне monitor. Возвращать snapshot результата, не мутировать общие списки из разных потоков. Проверить переключение серий при активной загрузке и prewarm.

### A08 — дублирующиеся resolver/discovery и неполная отмена — P1

`DetailsActivity.java:20`: `early` playback Future локален. Отмена `detailFuture` не отменяет его автоматически. После `early.get(2600, ...)` timeout код может запустить ещё один `playback()` при незавершённом первом. Catch общего Exception затрудняет различение отмены и ошибки источника.

`ApiRepository.resolveStreams():63` кэширует готовый результат, но не объединяет одновременно стартовавшие запросы одного URL. Несколько методов создают собственные `newFixedThreadPool`, поэтому пределы YoruApp не являются общим лимитом всех сетевых потоков.

**Изменить:** жизненный цикл запроса со всеми дочерними задачами, single-flight details/streams, общий бюджет запросов по хосту. При отмене останавливать сетевое соединение; одного `Future.cancel(true)` недостаточно для гарантированного прекращения HttpURLConnection. `InterruptedException` не превращать в обычный fallback.

### A09 — карточки пересоздаются вместо настоящего reuse — P2

`CalendarScreen.java:59` и `DetailsActivity.java:29`: `onBindViewHolder` делает `removeAllViews()` и создаёт содержимое заново. RecyclerView есть, но часть его выгоды теряется: новые TextView/ImageView/listeners/layout и повторные запросы постеров при скролле.

`DetailsActivity.render():22` полностью перестраивает карточку после частичных результатов; `episodes():27` содержит отдельный RecyclerView внутри ScrollView. Его высота передаётся как `visible*Ui.dp(this,78)` в `Ui.lp`, который сам переводит dp в px: требуется исправить двойное масштабирование и проверить плотности экрана.

**Изменить:** настоящие holder-поля и обновление значений, DiffUtil/payloads; у details — один вертикальный список секций и серий либо осознанно ограниченный блок без двойного dp. Сохранять позицию, выбранную серию и фильтры. Календарь уже имеет один верхнеуровневый список — это не ломать.

### A10 — лимит image disk cache зависит от количества файлов — P2

`ImageLoader.trimMaybe():42` не считает байты при числе файлов менее 360. Например, 300 файлов по 1 MiB уже превышают заявленный порог 160 MiB, но очистка не запустится. Cleanup не является строгим byte budget. Disk-hit в быстрой ветке не обновляет lastModified, поэтому сортировка не отражает все реальные использования.

**Изменить:** byte budget независимо от количества, trim после новых записей с гистерезисом, фоновый учёт размера, корректный access timestamp/индекс. Проверить конкурентный clear и записи старого generation.

### A11 — старт всё ещё выполняет лишнюю работу — P2

`YoruApp.onCreate()/afterFirstFrame():30–32`: lazy store/seed полезны, но `main.post()` не гарантирует выполнение после первого реально нарисованного кадра. Сразу стартуют проверка подписи, защита, расписание, seed, trim. Они могут конкурировать с пользовательским открытием каталога/плеера; getters SecureStore ждут synchronized preload при пересечении.

**Изменить:** измерить startup trace; вынести disk cleanup; прогрев низкого приоритета после реального кадра/idle, дедуплицировать календарь с экраном и update job. Не добавлять splash/loading shell и не ослаблять security check ради скорости.

## 5. Плеер, источники, сеть

### A12 — запуск ждёт resolver; iframe-код не подключён — P1

`PlayerActivity.loadEpisode():61` сначала `loadEpisode`, затем `resolveStreams`, лишь потом UI callback. `showVariant():65` опять делает resolver и запускает native либо rescue/error. В PlayerActivity нет вызова `YummyFrame.html`, `loadDataWithBaseURL` или загрузки iframe-URL; обнаруженные `loadUrl` загружают только `about:blank`. `YummyFrame.java` существует, но этого недостаточно для работающего iframe. При build одновременно создаются ExoPlayer и WebView; native-путь затем уничтожает WebView.

**Вывод:** требование памяти о немедленном iframe и неблокирующем захвате текущего потока не реализовано этим путём. Это статический вывод о маршрутизации, не заявление, что все источники не работают: прямые native streams могут успешно играть.

**Предложение:** отдельным согласованным изменением определить политику: известный stream → сразу native; поддерживаемый iframe → сразу разрешённый player URL и фоновый resolver; результат устаревшей сессии не переключает текущий просмотр. Не перезапускать успешно играющее видео при позднем discovery. Создавать WebView лениво. Не менять правила выбранной озвучки/auto-mode без регрессионной матрицы.

### A13 — сетевые таймауты не равны общему deadline — P2

`ApiRepository.java:78–...`: connect 2200 ms/read 3600 ms относятся к отдельным соединениям; redirect, mirror и resolver могут складывать задержки. `allCatalog():131` уже использует CompletionService, deadline 3600/4600 ms и ранний выход после достаточного результата — **это сохранить**.

Предложение: монотонные deadlines (`elapsedRealtime`), общий бюджет на пользовательское действие, abort оставшихся запросов, single-flight, backoff/cooldown для нестабильных источников. Возвращать быстрые результаты без ожидания сомнительных источников. Не добавлять proxy/API keys. Kodik 2026 сохранить; работоспособность каждого внешнего сайта проверять отдельно на устройстве.

### A14 — Referer и срок жизни stream cache требуют контекста — P2

`MediaCache.http():15`: общий Referer `https://yani.tv/` и cross-protocol redirects для всех потоков. `ApiRepository.resolveStreams()` хранит URL до 20 минут. Источники могут требовать другой Referer/headers или выдавать короткоживущие signed URL.

Предложение: передавать разрешённые source-specific request headers вместе с результатом resolver; обновлять протухший stream при 401/403 с одним ограниченным retry. Не логировать query tokens. Не объявлять 20 минут гарантией валидности потока.

## 6. Данные, безопасность и offline

### A15 — ошибки расшифровки маскируются пустой коллекцией — P1

`SecureStore.java:19–24`: невозможность открыть ключ/расшифровать значение приводит к пустому JSONObject; `loaded` устанавливается. При последующих успешных записях это может закрепить пустое состояние вместо восстановления.

Предложение: различать «первый запуск», «ключ временно недоступен», «повреждённые данные»; не перезаписывать исходное зашифрованное значение при ошибке чтения. Добавить безопасный экспорт/импорт пользовательской коллекции с версионированием и валидацией. Android Keystore/AES-GCM и запрет автоматического backup сохранить. Plaintext fallback не добавлять.

### A16 — HTTP разрешён глобально — P2

Manifest и `res/xml/network_security_config.xml`: cleartext разрешён для всех доменов. При этом WebView правильно запрещает file/content access, mixed content и отменяет SSL errors; это полезные меры, их не ослаблять.

Предложение: сначала инвентаризация реально необходимых HTTP endpoints, затем узкие domain exceptions; запрет downgrade для остального. `safeUrl` проверяет текст хоста, а не весь сетевой маршрут/DNS — не считать его абсолютной защитой от доступа к локальным адресам. Редиректы проверять на каждом шаге, где это контролируется приложением.

### A17 — offline-путь правильный, но lifecycle/cache нужно тестировать — P2

`MediaCache.offlineFactory()` использует cache без upstream: офлайн не должен незаметно догружать сеть. `OfflineExporter.export():35` не пересобирает HLS/DASH; SAF `ACTION_CREATE_DOCUMENT` для готового файла есть. Это соответствует продуктовым ограничениям.

Риски: первое создание DownloadHub/SimpleCache и `DownloadHub.get()` происходят также в PlayerActivity.onCreate, то есть могут затронуть диск на UI. `clearTemporary()` освобождает stream cache и удаляет WebView-каталоги; очистку во время активного playback нужно явно исключить или безопасно координировать.

Проверки: HLS и DASH в авиарежиме, pause/resume после убийства процесса, недостаток места, Android 15/16 timeout dataSync service, смена Wi-Fi/mobile, отмена системного проводника, внешний player без поддержки content URI. Не добавлять MP4-конвертацию.

## 7. Архитектура и сопровождение

Код физически сжат: 1860 строк Java на 603 KB; максимальная строка 4418 символов. ApiRepository — около 135 KB, PlayerActivity — 63 KB. «Мало строк» здесь не означает простоту. Большие методы смешивают сеть, выбор источника, UI, сохранение и обработку ошибок.

План без большой переписи:

1. Отдельный форматирующий commit без изменения поведения. Чистый Java/XML/Groovy без комментариев в коде, согласно AGENTS.
2. NetworkClient + RequestBudget + RequestCancellation.
3. SourceAdapter/fixtures для каждого источника; нормализованный Anime/Episode/Variant result.
4. PlaybackCoordinator со state machine: session/episode/voice/resolving/playing/fallback/offline.
5. Repository слои для metadata, collection/progress и downloads; immutable snapshots для UI.
6. UI sections/holders с диффами вместо полной перерисовки.
7. Типизированные ошибки: offline, timeout, parser changed, unavailable episode, expired stream, storage error. Пользовательские сообщения простые; техническая диагностика локальная и без токенов/истории просмотра.

Не требуется Kotlin/Compose/Room/OkHttp ради самого перехода. Добавление библиотеки оправдывать конкретным снижением сложности и проверять влияние на APK/startup. Media3 1.5.1 и другие pinned dependencies обновлять отдельным этапом после проверки release notes/совместимости, не называть их уязвимыми только из-за возраста.

## 8. Как измерять эффект

Это **план измерений**, не результаты текущего аудита.

- Минимум одно слабое физическое устройство и одно современное; API 26/28 для совместимости и API 35/36 для фоновых ограничений.
- Фиксировать модель, Android, build variant, исходный commit, температуру/режим питания и сетевой профиль.
- Cold start и warm start: first frame + момент появления полезного контента, p50/p95; 20 повторов как начальный набор, для стабильного p95 расширить.

## 9. Тесты и CI

Минимум до следующего релиза:

- Unit fixtures: парсеры источников, пустые/изменённые ответы, отсутствие предпочитаемой озвучки, будущие серии, дробные номера, дедупликация сезонов, реальные 1440p/2160p.

- Concurrency tests: переполнение очередей, отмена родителя/детей, быстрый поиск, повторное открытие экрана, download+prewarm+switch episode.
- Instrumentation: cold start, rotate/background/PiP, permissions, progress persistence, HLS/DASH offline, SAF.
- CI: Java/XML parse → unit test → lint → debug/release assembly → APK verify (`apksigner`, package/version, ZIP integrity, SHA-256).
- Source ZIP из явного allowlist без keystore, credentials, build/cache, других продуктов и старых ZIP. Проверить debug build из его распаковки.
- Workflow: минимальные permissions; ограничить публикацию доверенной текущей веткой; concurrency на сборки; загружать диагностические отчёты при failure. Обновления actions/dependencies отдельными проверяемыми изменениями.
